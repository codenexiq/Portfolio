## Purpose

A portfolio is more than a list of project links. It should help visitors understand the problem a project addresses, the role played in its development, the choices made during implementation, and the results that can be demonstrated.

This repository aims to support that goal by providing a consistent presentation for each selected project.

### Core Objectives

- Present selected projects in a clear and accessible format.
- Explain each project's purpose and intended audience.
- Describe the actual technologies used.
- Show screenshots or demonstrations when available.
- Link to source code where it is public.
- Separate completed work from experiments and work in progress.
- Make contact and collaboration options easy to find.
- Keep claims factual and verifiable.
- Make the repository easy to maintain.
- Improve the documentation as the portfolio grows.

### What Success Looks Like

- A visitor can understand the portfolio's purpose within a few seconds.
- Project cards or entries have descriptive titles.
- Every published link works.
- Images have meaningful alternative text.
- Project statuses are honest and up to date.
- Installation instructions work when the repository contains runnable code.
- Contact information is current.
- The README renders correctly on GitHub.
- The repository does not expose secrets or private data.
- The project catalogue is useful on both desktop and mobile screens.

## Frontend Engineering

Frontend projects should prioritize understandable interfaces, reliable state handling, and consistent visual behavior.

### Common Areas of Focus

- Semantic HTML
- Component composition
- Clear component responsibilities
- Reusable UI patterns
- Responsive layouts
- Loading and error states
- Form validation
- Empty states
- Keyboard navigation
- Accessible labels
- Image optimization
- Appropriate use of client-side JavaScript
- Predictable routing
- Useful page metadata

### Component Design

A component should have a clear purpose and a manageable API.

Recommended practices:

- Use descriptive names.
- Keep unrelated behavior separate.
- Avoid unnecessary prop complexity.
- Reuse components when reuse improves consistency.
- Keep one-off components simple.
- Make loading and failure behavior explicit.
- Document unusual constraints.
- Prefer readable code over clever shortcuts.

### State Management

Choose state management based on the complexity of the application.

- Keep local state close to where it is used.
- Avoid duplicating derived state.
- Treat server data and UI state as distinct concerns.
- Handle asynchronous operations explicitly.
- Prevent duplicate submissions where appropriate.
- Show feedback for successful and unsuccessful actions.
- Consider stale data and race conditions.

### Forms

Forms should explain what is expected and how to correct errors.

- Use appropriate input types.
- Label every input.
- Validate on the server as well as the client.
- Preserve user input when a recoverable error occurs.
- Display actionable validation messages.
- Prevent accidental double submission.
- Make success states clear.
- Test keyboard and screen-reader behavior.

## Backend Engineering

Backend code should make data handling, access control, and error behavior explicit.

### API Design

- Use predictable routes.
- Choose appropriate HTTP methods.
- Return suitable status codes.
- Validate request parameters and bodies.
- Keep response formats consistent.
- Document authentication requirements.
- Apply pagination to large collections.
- Avoid exposing internal stack traces to clients.
- Use rate limiting where appropriate.
- Version APIs when compatibility requires it.

### Error Handling

- Use centralized error handling where practical.
- Log useful diagnostic context.
- Avoid logging passwords, tokens, or sensitive payloads.
- Distinguish expected validation errors from unexpected failures.
- Return stable error formats to clients.
- Include request identifiers where useful.
- Ensure rejected asynchronous operations are handled.

### Authentication

- Use a well-reviewed authentication approach.
- Store password hashes, never plain-text passwords.
- Set secure cookie attributes when cookie authentication is used.
- Keep access tokens short-lived when appropriate.
- Rotate and revoke credentials according to the application's needs.
- Protect sensitive routes on the server.
- Avoid treating frontend-only route protection as authorization.

### Authorization

- Check permissions on every protected operation.
- Apply least-privilege access.
- Verify ownership of user-specific resources.
- Avoid trusting identifiers supplied by the client.
- Test both allowed and denied access paths.

## Databases and Data

Database choices should follow project requirements rather than portfolio trends.

### Data Modeling

- Identify entities and relationships.
- Use consistent naming.
- Add constraints where they protect data integrity.
- Choose appropriate indexes.
- Avoid storing redundant data without a reason.
- Define deletion and retention behavior.
- Document important business rules.

### Migrations

- Keep schema changes versioned.
- Review destructive changes carefully.
- Back up production data before risky migrations.
- Test migrations against representative data.
- Plan for deployment order and compatibility.
- Avoid editing migration history that has already been applied in shared environments without a safe plan.

### Data Protection

- Collect only necessary information.
- Limit access to sensitive data.
- Avoid exposing internal database errors.
- Use encrypted connections where supported.
- Define backup schedules.
- Test restoration procedures.
- Follow applicable privacy and retention requirements.

## Performance

Performance improvements should be measured and prioritized according to their effect on users.

### Frontend Performance

- Optimize images.
- Avoid unnecessary JavaScript.
- Load non-critical resources when needed.
- Use appropriate caching.
- Avoid layout shifts.
- Split large bundles when beneficial.
- Keep third-party scripts under review.
- Use server rendering or static generation where appropriate.
- Avoid repeated network requests.
- Measure real user behavior where suitable.

### Backend Performance

- Inspect slow queries.
- Add indexes based on actual query patterns.
- Use pagination for large result sets.
- Avoid repeated expensive work.
- Cache only when invalidation can be handled correctly.
- Set sensible timeouts.
- Avoid unbounded background tasks.
- Monitor resource use during traffic spikes.

### Performance Reporting

When sharing metrics, include the measurement context.

- Test date.
- Device or test environment.
- Network conditions.
- URL or route.
- Tool used.
- Metric name.
- Result.
- Known limitations.

Do not publish performance numbers without a reproducible measurement.

## Security Principles

Security practices depend on the application's risk profile, but the following baseline is broadly useful.

- Never commit secrets.
- Keep dependencies updated with a review process.
- Validate input on the server.
- Apply authorization checks to protected resources.
- Use HTTPS in production.
- Configure security headers where appropriate.
- Protect against injection vulnerabilities.
- Use secure password hashing.
- Restrict file uploads by type, size, and content where applicable.
- Avoid exposing detailed production errors.
- Apply rate limits to sensitive endpoints.
- Keep access credentials out of logs.
- Review third-party integrations.
- Back up critical data.
- Document incident response steps.
- Remove unused credentials and services.

### Secret Handling

Use environment variables or a suitable secret manager for private configuration. A `.env.example` file may list variable names and safe placeholder values, but it should never contain real credentials.

### Dependency Maintenance

- Review security advisories.
- Update compatible dependencies regularly.
- Test after updates.
- Avoid blindly installing unknown packages.
- Keep lockfiles under version control when appropriate.
- Remove unused dependencies.

## Troubleshooting

### Dependencies Fail to Install

Possible checks:

1. Confirm the required runtime version.
2. Use the package manager associated with the lockfile.
3. Check network access to the package registry.
4. Review the complete error output.
5. Avoid deleting the lockfile as a first response.
6. Check whether a native dependency requires additional build tools.

### Development Server Does Not Start

- Confirm the command exists in `package.json`.
- Check whether the port is already in use.
- Review missing environment variables.
- Confirm dependencies installed successfully.
- Read the first meaningful error in the terminal.
- Check for incompatible runtime versions.

### Build Fails

- Run the build locally.
- Check the first fatal error rather than only the final summary.
- Confirm the deployment runtime matches supported requirements.
- Verify imports and file-name casing.
- Check environment variables required at build time.
- Review native package compatibility.
- Ensure generated files are not missing.

### Images Do Not Load

- Check the image path.
- Confirm the file exists in the expected directory.
- Review case sensitivity.
- Check allowed remote image hosts if the framework requires configuration.
- Inspect the browser network panel.
- Verify that the deployed build includes the asset.

### API Requests Fail

- Inspect the request URL.
- Check the response status.
- Review the browser network panel.
- Confirm the backend is reachable.
- Verify CORS configuration when browser cross-origin requests are involved.
- Check authentication headers or cookies.
- Review server logs.
- Confirm that the frontend uses the correct environment URL.

### CORS Errors

CORS is enforced by browsers for cross-origin requests. Review the backend's allowed origins and the exact `Origin` header sent by the browser.

- Allow only trusted origins.
- Include the correct scheme and hostname.
- Handle credentials consistently.
- Avoid using a wildcard origin with credentialed requests.
- Check preflight requests when relevant.
- Do not treat CORS as a substitute for authentication or authorization.

### Deployment Works but the Site Is Old

- Confirm the expected commit was deployed.
- Check the hosting provider's deployment status.
- Review build logs.
- Confirm the correct output directory or runtime version is active.
- Check caching behavior.
- Verify that a previous release is not still serving traffic.
- Clear local browser cache only after confirming deployment status.

### Environment Variable Is Missing

- Confirm the variable name exactly matches the code.
- Check the environment where it is defined.
- Rebuild if the framework embeds public variables at build time.
- Restart the application if runtime configuration requires it.
- Never print secret values to diagnose the issue.

### Unexpected JavaScript Error

- Reproduce the issue.
- Inspect the browser console.
- Inspect the stack trace.
- Check whether the error follows a failed API request.
- Review recent changes.
- Test a clean production build.
- Confirm that old and new assets are not being mixed.
